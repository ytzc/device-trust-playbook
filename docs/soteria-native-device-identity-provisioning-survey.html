Soteria 已確認的 DevID 加密基礎

  • TRNG (MSG0=0x4) — 真亂數，key gen 基礎
  • RSA (MSG0=0x3) — 512/1024/2048-bit，PKCS#1 v1.5
  • AES (MSG0=0x1) — 對稱加密，cert/key 儲存保護
  • HMAC (MSG0=0x2) — SHA-256/384/512，integrity
  • Black Key (MSG0=0x12/0x14) — key wrapping 保護機制
  • OTP — 8KB 不可更改儲存
  • Secure Boot anchor (MSG0=0x15/0x16) — identity verification

DevID 關鍵待確認能力

  • ECDSA / ECC P-256 — IoT 標準；RSA 較大，需確認
  • Non-exportable key gen API — "生成私鑰，只導出公鑰"的封裝 API
  • OTP 空間規劃 — 8KB 夠不夠 DevID key + cert？
  • Certificate 儲存方案 — 外部 flash + AES_BK？
  • mTLS handshake flow — Linux TLS → Soteria 簽名工作流
  • Linux 直接存取 Soteria — 或必須通過 Secure World？
  • Firmware measurement / PCR — 未來 RA 需求（高優先）

OP-TEE fTPM Path 分析

OP-TEE fTPM 在 TX8 上的記憶體需求、整合成本與 DevID 能力。

OP-TEE 執行位置： OP-TEE OS 執行在 主 ARM SoC 的 TrustZone Secure World，不是執行在 Soteria hRoT 上。Soteria 是 AHB-connected 硬體 IP，OP-TEE 可在 Secure World 透過 AHB driver 存取 Soteria。

OP-TEE fTPM 技術堆疊

Linux (Normal World)
    │ /dev/tpmX  ←  TSS2 / OpenSSL TPM2 Provider（與 hTPM 完全相同 API）
    ▼
tpm2-abrmd (TPM resource manager daemon)
    │ TEE Client API / OP-TEE driver
    ▼
OP-TEE OS (Secure World, ARM TrustZone)
    │
    ▼
fTPM Trusted Application (TA)
    │ based on Microsoft TPM 2.0 Reference Implementation
    ▼
OP-TEE Secure Storage (SFS)  ←  flash-backed, HUK-encrypted

記憶體佔用分析

元件典型需求

⚠️ TX8 系統記憶體限制未確認，OP-TEE 佔用可能是問題

TX8 OP-TEE fTPM 前提條件

  • ⚠️ TX8 主 SoC 支援 ARM TrustZone（未確認）
  • ⚠️ BSP 包含 TF-A（BL1/BL2/BL31）（未確認）
  • ⚠️ OP-TEE OS 可在 TX8 BSP 上啟用（未確認）
  • ⚠️ fTPM TA 可編譯並整合（未確認）
  • ⚠️ Secure Boot 啟用（Phase 3 需求）
  • ⚠️ TX8 系統記憶體足夠支援 OP-TEE

Device Trust Abstraction Layer

Backend-agnostic 設計，讓 TTPS DI 不依賴具體 RoT 後端，保留未來擴展空間。

設計動機： 無論 TX8 最終採用 Soteria-native 還是 OP-TEE fTPM，TTPS DI 服務不應直接依賴底層 RoT API。設計 backend-agnostic 抽象層，讓不同平台（TX8、PLANET MTK、x86）使用相同上層 API，未來 Remote Attestation 也不需要重寫上層邏輯。
