01

Root of Trust 方法總覽

各種 RoT 技術的定位、使用場景與信任基礎。

核心原則： RoT（Root of Trust）是設備安全的信任起點。hardware RoT 將 private key 和 secret 保護在硬體邊界內，讓 OS 無法直接讀取或提取。這是 CRA-ready 設備安全的技術基礎。

hTPM

Hardware TPM — 實體晶片

Dedicated 硬體 TPM 2.0 晶片。x86 平台標準方案。Discrete（焊在主板上）或 Integrated（Intel PTT / AMD PSP fTPM）。

📌 x86 Default Path

fTPM

Firmware TPM — TEE 中的軟體 TPM

在 TEE（如 ARM TrustZone / OP-TEE）Secure World 中執行的 TPM 實作。對外提供 TPM 2.0 API。ARM 平台主要路線。

📌 ARM + OP-TEE Path

vTPM

Virtual TPM — 虛擬化環境

在 VM / hypervisor 環境中使用的虛擬化 TPM。常見實作：swtpm。信任基礎是 hypervisor，不適合生產設備。

📌 VM/KVM/QEMU 測試用

hRoT

Hardware Root of Trust — 專用安全晶片

專用硬體安全模組，提供 secure key storage、設備身份、可能的 firmware integrity。例如 Soteria hRoT（TX8）、NXP ELE。

📌 TX8 / Vendor-specific

Secure Element（SE）

External Secure Element

可加入現有平台的外接安全元件，提供 hardware-isolated key storage。透過 PKCS#11 標準介面整合。適合 Legacy 平台補強。

📌 Legacy MIPS Path B 選項

PUF

Physical Unclonable Function

利用晶片製造差異產生唯一識別碼（device fingerprint）。可作為 key derivation 的 root secret。部分 SoC 內建（如 NXP ELE）。

📌 Key derivation 基礎

Pure Software Key Storage

不建議用於生產設備

Key 儲存在 OS 檔案系統，無硬體保護邊界。OS root 使用者可讀取或複製。只適合開發環境，CRA production 場景不建議。

❌ 不適合 CRA production

fTPM vs vTPM — 關鍵區分

John 特別提醒這兩者不一樣，請嚴格區分使用場景。

⚠ 常見混淆： 兩者名稱相似，但使用場景完全不同。fTPM 用於實體 embedded 設備；vTPM 用於 VM 虛擬化環境。不要混用。

04

OP-TEE fTPM TA — ARM 平台主要路線

OP-TEE fTPM 的技術架構、整合方式與 PLANET 適用性。

OP-TEE fTPM TA 技術架構

ARM 主要路線
TrustZone 架構
  • Normal World：Linux OS / OpenWRT，透過 TSS2 library 發送 TPM 命令
  • Secure World：OP-TEE OS 執行環境，fTPM TA 在其中運行
  • 通訊路徑：Normal World → TEE Client API → OP-TEE OS → fTPM TA
  • 記憶體隔離：TZASC / TZMA 確保 Secure World 記憶體無法從 Normal World 存取
關鍵元件
  • TF-A（Trusted Firmware-A）：BL1/BL2/BL31 bootloader，建立安全的 boot chain
  • OP-TEE OS：BL32，TrustZone Secure World TEE kernel
  • fTPM TA：在 OP-TEE 中運行的 TPM 2.0 Trusted Application
  • tpm2-abrmd：TPM Access Broker & Resource Manager daemon

整合 API 與 FiduciaEdge 使用方式

API 介面（對外與 hTPM 一致）
  • TSS2：TPM Software Stack 2（tpm2-tss），Linux 標準 TPM library
  • OpenSSL TPM2 Provider：tpm2-openssl，透過 OpenSSL 使用 TPM key
  • PKCS#11 bridge：tpm2-pkcs11，PKCS#11 標準介面整合
  • tpm2-tools：命令列工具，方便測試與自動化
FiduciaEdge Phase 1 任務（PLANET）
  • TTPS DI 移植：Ubuntu + hTPM → MTK OpenWRT + OP-TEE fTPM
  • fTPM TA 啟用與 TSS2 stack 整合
  • Hardware-bound IDevID / LDevID provisioning
  • CLI 工具自動化 DI 流程
05

Microsoft TPM 2.0 Reference Implementation

OP-TEE fTPM 通常基於此實作，了解其定位有助於技術溝通。

什麼是 MS TPM 2.0 Reference Impl

  • Microsoft 開源的 TPM 2.0 完整 firmware 實作（C 語言）
  • GitHub: microsoft/ms-tpm-20-ref
  • 符合 TCG TPM 2.0 specification Part 1–4
  • 可移植到各種 TEE / firmware 環境
  • 是許多 ARM fTPM TA 的基礎實作（包括 OP-TEE fTPM）
  • 與 Windows fTPM（Intel ME / AMD PSP）使用相同基礎

在 OP-TEE 中的使用

  • OP-TEE fTPM TA 移植自 MS TPM 2.0 Reference Impl
  • 提供完整 TPM 2.0 命令集支援（Key Gen, Sign, PCR, Quote 等）
  • Storage: 使用 OP-TEE Secure Storage（加密於 hardware-protected key）
  • Entropy: 依 OP-TEE platform entropy source（ARM TRNG 或其他）
  • ⚠ 需確認：John 使用的 OP-TEE fTPM 版本與 MS Ref Impl 基礎關係
06

swtpm — vTPM 的常見實作

FiduciaEdge CI/CD 測試環境使用的 virtual TPM 後端。

swtpm 定位與使用方式

開發測試用 不可用於生產
技術背景
  • 開源軟體 TPM 2.0 模擬器，作者：Stefan Berger（IBM）
  • GitHub: stefanberger/swtpm
  • 提供與實體 TPM 相同的 API（通過 socket 或 char device）
  • KVM/QEMU 透過 -tpmdev emulator,id=tpm0,chardev=chrtpm 啟用
與 KVM / QEMU 整合
  • QEMU 透過 tpm-tis-device（virtio-tpm）或 tpm-tis（ISA）暴露給 guest OS
  • Guest Linux 使用標準 TPM2 Provider，感覺不到是 vTPM
  • 適合測試 TTPS DI flow、Phase 1/2/3 功能驗證
限制（不可用於生產）
  • TPM state 存在 host 檔案系統（無硬體保護）
  • hypervisor / host OS 可讀取 TPM internal state
  • 不符合 CRA production 設備的 hardware RoT 要求
  • FiduciaEdge 使用場景：CI/CD pipeline 測試環境，不是交付給客戶的 production 設備方案

Soteria hRoT — TX8 Vendor-specific RoT

不走 TPM API，需要另外確認能力。

⚠ 注意： Soteria hRoT 是 hardware RoT，但不等於 TPM。不要把它說成「TX8 的 TPM」。正確說法是「TX8 的 hardware Root of Trust 是 Soteria hRoT，使用 vendor-specific API」。

Soteria hRoT 技術定位

TX8 only Phase 3 待確認
已知資訊
  • Techmation TX8 內建 Soteria hardware RoT 模組
  • 提供 hardware-level key isolation（hardware boundary）
  • 透過 Soteria vendor SDK / proprietary API 存取
  • 不使用 TCG TPM 2.0 standard API（非 TSS2 compatible）
  • Phase 1（device identity）與 Phase 2（key protection）技術上可行
待確認（Phase 3 阻擋條件）
  • Soteria API 是否支援：secure key storage、non-exportable key generation
  • Soteria 是否有 PCR-like measurement slots（Measured Boot 基礎）
  • Soteria 是否支援 attestation quote / signed measurement report
  • Soteria SDK 文件取得、custom adapter 工程量估算
整合架構（已知）
  • 需開發 custom adapter layer：Soteria vendor API → TTPS DI flow
  • 工程量高於標準 TPM2 Provider path，但避免硬體重設計
  • 若 Phase 3 不可行，TX8 仍可在 Phase 1/2 提供有意義的 CRA support
08

RoT 在 CRA Support 中的角色

RoT 是 CRA-ready 安全基礎，但不等於完整 CRA compliance。

定位說法： RoT（hTPM / fTPM / hRoT）提供 device identity、key protection、firmware integrity、attestation foundation，是 CRA compliance support 的技術基礎，但 CRA 合規還需要 OEM 執行 vulnerability handling、security updates、conformity assessment 等額外工作。
CRA-related CapabilityRoT 提供的技術基礎CRA Annex I 對應還需要什麼
Device Identity Hardware-bound IDevID/LDevID，non-exportable key in RoT (2)(d) AuthN & Identity OEM 應用層 AuthZ policy
Key Protection Private key 不離開 hardware boundary（VPN/mTLS hardening） (2)(e) Confidentiality 所有管理介面強制 TLS
Firmware Integrity Secure Boot + Measured Boot，每個 boot 階段 hash 進 PCR (2)(f) Integrity OEM 需建立 Secure Boot chain + SBOM pipeline
Attestation Foundation Signed attestation quote（hardware-backed），NMS 可驗證 (2)(f)(k)(l) Integrity/Monitoring NMS verifier + Known-Good baseline DB
Attack Surface Reduction Cert-based auth 取代預設密碼，DI 消除臨時設定路徑 (2)(j) Attack surface 停用 JTAG/SWD；關閉未使用 port
Vulnerability Handling SBOM 支援 CVE correlation Part II (2)–(6) OEM 必須建立 PSIRT + CVD policy
