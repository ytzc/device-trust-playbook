一分鐘總心智模型
One-Minute Mental Model — 7 句話記住核心
1 · Device Trust 核心
設備有可信身份（DevID）、私鑰不外洩（non-exportable）、開機可驗證（Secure/Measured Boot）、連線可被認證（mTLS）、未來可遠端 attestation。 這是一個端到端的安全堆疊，而不只是一個協議或一個晶片。
2 · Root of Trust 是什麼
信任鏈的起點硬體模組，負責 key 保護、crypto 加速、secure boot 驗證。 不等於 CRA compliance，但是 CRA-ready 的技術基礎。沒有 RoT，上層的一切安全保證都是空中樓閣。
3 · TPM / fTPM / hRoT 家族
hTPM 是標準晶片（x86 平台）、fTPM 是 TrustZone 裡的 firmware TPM（ARM 平台）、vTPM 是 VM 用的（非生產，僅測試）、Soteria hRoT 是 vendor-specific 硬體 IP（TX8 專屬，非 TPM 標準但功能類似）。 選哪個看平台，不是看偏好。
4 · Soteria-native path（TX8 研究方向）
TX8 已有 Soteria hRoT，先研究能否直接用 Soteria AHB API 支援 DevID / mTLS / provisioning，不需要先導入完整 OP-TEE fTPM stack。 記憶體佔用更低、整合更簡單；缺點是 API 非 TPM 標準，Phase 3 attestation 需要額外設計。
5 · OP-TEE fTPM path
需要 TPM 2.0 API / PCR / Quote / 標準 attestation 時選這條路。 前提是 SoC 支援 ARM TrustZone，且有 BSP 支援（估計 +2–4 週工程量）；記憶體佔用較高（4–16 MB）。 對 PLANET MTK 平台是主要路徑，對 TX8 則是 Path B 候選。
6 · CRA-ready 定位
我們提供 CRA-ready 技術基礎與 evidence 準備，不等於保證 full CRA compliance（法律責任在 OEM）。 永遠不說「guarantee compliance」，也不說「TPM equals CRA」。 正確說法：「我們的平台提供 CRA-ready 技術基礎，協助 OEM 準備 evidence。」
7 · 設計原則：Device Trust Abstraction Layer
Backend-agnostic 介面設計：上層 TTPS DI 不直接依賴 Soteria / TPM / fTPM，透過 dt_generate_key / dt_sign / dt_store_cert 等 API 操作。 未來可換後端（Soteria → fTPM），未來接 Remote Attestation，架構不需要大改。

名詞卡片庫
Vocabulary Flashcards — 27 個核心名詞，手機複習用
01 · Device Trust
設備信任
確保設備身份真實、金鑰安全、韌體完整、通訊可信的整體安全架構。
💬 「Device Trust 是讓設備從出廠到運行都有可驗證的信任鏈」
⚠️ 不只是 TLS，是完整安全堆疊
02 · Device Identity
設備身份
設備在網路中的可驗證唯一身份，通常以 X.509 憑證表示。
💬 「就是設備的數位身份證，憑證 + 私鑰組合」
⚠️ 不等於 IP/MAC，要有硬體保護的私鑰
03 · Device ID / DevID
IEEE 802.1AR 設備身份規範
IEEE 802.1AR 定義的設備身份規範，分 IDevID 和 LDevID。
💬 「DevID 是 IEEE 標準化的設備身份，有嚴格的 non-exportable key 要求」
⚠️ DevID ≠ 一般的 Device ID（後者是泛稱）
04 · IDevID
Initial Device Identifier
出廠時由製造商安裝的不可更換初始身份，與設備終身綁定。
💬 「就像設備的出生證明，出廠燒錄，終身不換」
⚠️ 一旦安裝不可更改，OTP 儲存
05 · LDevID
Locally Significant Device Identifier
現場部署後由組織發放的可更換操作身份。
💬 「就像工作證，可以更換、可以撤銷」
⚠️ 比 IDevID 靈活，可以 renew，但需要 IDevID 才能初始建立信任
06 · Device Initialization
設備初始化
出廠時燒錄 RoT keys / OTP / IDevID，設定 secure boot 的過程。
💬 「出廠前的設定作業：燒 key、鎖 OTP、設定 secure boot」
07 · Device Registration
設備註冊
設備第一次向後端系統登記身份，讓後端知道「這台設備存在且合法」。
💬 「設備出廠後，第一次向雲端說我是誰、我的憑證是什麼」
08 · Device Onboarding
設備上線
設備完成認證後，取得網路存取權限、配置、服務授權的完整流程。
💬 「從設備插電到可以正常工作的完整流程，包含認證、配置、授權」
⚠️ Onboarding 比 Registration 範圍大，包含 provisioning
09 · Secure Provisioning
安全佈建
安全地為設備安裝 credentials、配置、軟體的過程。
💬 「在安全環境下把設備需要的 key、cert、config 裝進去」
⚠️ 不只是安裝軟體，安全性是核心要求
10 · Root of Trust (RoT)
信任根
整個信任鏈的起點硬體模組，提供 key 保護、crypto、secure boot。
💬 「RoT 就是最底層的安全基礎，一切信任從這裡開始」
⚠️ RoT ≠ CRA compliance，只是技術基礎
11 · hTPM
Hardware TPM
實體 TPM 2.0 晶片，x86 平台標準方案，最好溝通。
💬 「主機板上的 TPM 晶片，x86 伺服器/PC 的標配 RoT」
12 · fTPM
Firmware TPM
在 TrustZone Secure World 執行的 TPM firmware，提供與 hTPM 相同 API。
💬 「跑在 ARM TrustZone 裡的 TPM 軟體，從外面看起來和 hTPM 一樣」
⚠️ fTPM ≠ vTPM（fTPM 是實體設備，vTPM 是 VM）
13 · vTPM
Virtual TPM
VM/KVM/QEMU 環境中的虛擬化 TPM，信任基礎是 hypervisor。
💬 「VM 用的軟體 TPM，只適合開發測試」
⚠️ 絕對不能用於生產 IoT/embedded 設備
14 · hRoT
Hardware Root of Trust
專用硬體安全模組，non-TPM，vendor-specific API。
💬 「和 TPM 功能類似，但 API 不標準，Soteria 就是 hRoT 的例子」
15 · Soteria hRoT
TX8 Hardware Security IP
TX8 上的 hardware security IP，RISC-V ibex + 8KB OTP + AES/HMAC/RSA/TRNG，透過 AHB MSG 命令操作。
💬 「TX8 內建的硬體安全模組，透過 AHB bus 存取，非 TPM 標準」
⚠️ OP-TEE 不跑在 Soteria 上
16 · OP-TEE
Open Portable Trusted Execution Environment
ARM TrustZone Secure World 的開源 Secure OS。
💬 「ARM 平台的安全 OS，跑在主 SoC 的 Secure World 裡，fTPM TA 就住在裡面」
⚠️ OP-TEE 跑在主 SoC，不是跑在 Soteria
17 · fTPM TA
fTPM Trusted Application
跑在 OP-TEE 裡的 TPM-like 應用，通常基於 MS TPM 2.0 Ref Impl。
💬 「OP-TEE 裡的 TPM 應用程式，對外提供標準 TPM 2.0 命令」
18 · Secure Element (SE)
安全元件
外接安全晶片，I2C/SPI/USB 介面，PKCS#11 API。
💬 「可加到現有板子的外接安全晶片，適合 Legacy 平台補強」
⚠️ 通常不支援 PCR/Measured Boot/attestation
19 · PUF
Physical Unclonable Function
利用晶片製造差異產生唯一 fingerprint，作為 key derivation 基礎。
💬 「晶片的指紋，每顆都不一樣，用來衍生設備唯一 key」
⚠️ PUF 本身不是 TPM，需搭配 key management
20 · Secure Boot
安全開機
開機守門員：驗證韌體/OS 簽名，拒絕未授權的 image 開機。
💬 「不讓壞的軟體開機，簽章驗不過就停下來」
⚠️ Secure Boot 不記錄，只阻擋
21 · Measured Boot
量測開機
開機記錄員：量測每個開機 component 的 hash，存入 PCR。
💬 「把開機過程都量測記錄下來，不阻擋但留下可驗證的記錄」
⚠️ Measured Boot 不阻擋，需配合 Remote Attestation 才有意義
22 · Remote Attestation (RA)
遠端認證
把 Measured Boot 的 PCR 量測結果，用 TPM AIK 簽名，傳給遠端 Verifier 驗證。
💬 「讓遠端可以確認：這台設備開機狀態是乾淨的」
⚠️ 需要 Measured Boot + TPM Quote 能力，Phase 3 才有
23 · mTLS
Mutual TLS
雙向 TLS 憑證認證，設備和後端互相驗證身份。
💬 「設備用 DevID cert 認證自己，後端也用 cert 認證自己，雙向都驗」
⚠️ 私鑰必須在硬體邊界內（non-exportable），否則 mTLS 保護力很弱
24 · CRA-ready
CRA 就緒技術基礎
技術控制到位、evidence 可準備，能支援 OEM 進行合規評估。
💬 「我們的平台有 CRA 需要的技術基礎，能幫 OEM 準備 evidence」
⚠️ 不等於通過合規評估
25 · CRA compliance support
合規支援服務
FiduciaEdge 提供技術實作和 evidence 準備，但法律合規責任在 OEM。
💬 「我們支援 OEM 做合規，但合規的法律責任是 OEM 的」
26 · Full CRA compliance
完整 CRA 合規
通過 conformity assessment、取得 CE marking，法律責任完全在 OEM 製造商。
💬 「這是 OEM 的責任，不是 FiduciaEdge 能保證的」
⚠️ FiduciaEdge 永遠不說「我們保證完整 CRA 合規」
27 · Device Trust Abstraction Layer
設備信任抽象層
Backend-agnostic 介面層，dt_generate_key / dt_sign / dt_store_cert 等 API，支援 Soteria / TPM / fTPM 後端。
💬 「讓上層不需要知道底層是什麼 RoT，未來換後端不用重寫」

5
Soteria-native Path 記憶模型
直接用 Soteria AHB API 做 DevID / mTLS / Provisioning
一句話：Soteria-native path 的目標是不用先導入完整 OP-TEE fTPM，直接用 Soteria hRoT 支援設備身份、金鑰保護、設備註冊與 mTLS。

5.1 製造 → 部署 → 運行流程

1
Factory：安裝 ROK（INSTALL_ROK 0x11），燒 OTP，鎖 debug port。出廠前的安全設定。
2
Key Gen：Soteria TRNG → Black Key 保護私鑰在硬體邊界內（non-exportable ⚠️TBC）。公鑰可導出（⚠️TBC）。
3
CSR：SW 層做 ASN.1 encoding + Soteria RSA 簽名（MSG0=0x3）→ 送 CA 簽發 IDevID Certificate。
4
Cert 儲存：IDevID key material → OTP（8KB）；X.509 cert → 外部 flash + Black Key 保護（⚠️TBC）。
5
mTLS：Soteria RSA 簽名做 TLS client auth，私鑰不離 Soteria（⚠️TBC workflow）。
6
Future：Soteria firmware measurement + attestation quote（❌TBC）→ CRA Phase 3 需求。

OP-TEE fTPM 記憶模型
什麼時候需要它、怎麼運作、成本與風險
問題答案
OP-TEE 跑在 Soteria 上嗎？❌ 不。OP-TEE 跑在主 ARM SoC 的 TrustZone Secure World。Soteria 是獨立 AHB 硬體 IP，被 OP-TEE driver 透過 AHB 存取。
fTPM TA 是什麼？跑在 OP-TEE 裡的 Trusted Application，通常基於 Microsoft TPM 2.0 Reference Implementation，對外提供標準 TPM 2.0 命令介面。
對外看起來是？和 hTPM 一模一樣：/dev/tpmX → tpm2-abrmd → TSS2 → OpenSSL TPM2 Provider。上層感覺不到差別。
什麼時候需要它？需要 TPM 2.0 API 相容性、PCR/Measured Boot、TPM2_Quote、ECDSA，或客戶要求標準 TPM evidence 時。
TX8 前提？TX8 主 SoC 支援 TrustZone + BSP 有 TF-A（BL31）+ OP-TEE OS（BL32）+ fTPM TA。目前全部未確認 ⚠️
John 擔心什麼？Memory footprint（4–16 MB）、BSP 四層整合成本（TF-A + OP-TEE OS + fTPM TA + Secure Storage）、若只需 DevID/mTLS 不值得。
能不能不用？若 Soteria-native path 足以支援 DevID/mTLS，短期可以不用。Phase 3 Remote Attestation 仍需確認 Soteria 或改用 fTPM。
Soteria 能幫 fTPM 做什麼？Path C (Hybrid)：Soteria 作為 OP-TEE fTPM 底層 hardware-backed secure storage，Black Key 保護 fTPM persistent keys。整合複雜度最高。

設備生命週期記憶流程
從出廠到 CRA Evidence — 每步一句話
製造
Device Initialization — 燒 RoT keys / OTP / IDevID root material，設定 Secure Boot，鎖 debug。出廠前的安全設定，這步做不好後面全垮。
佈建
Secure Provisioning — 安全地安裝 credentials（cert、key）、配置、軟體。把設備需要的身份材料安全地「塞進去」。
首次
Device Registration — 第一次向後端登記身份，後端建立設備記錄。設備向後台說「我來報到了，這是我的 DevID cert」。
上線
Device Onboarding — 完成認證後取得網路存取、配置、服務授權（BRSKI / FDO 流程）。從插電到可以工作的完整流程。
通訊
mTLS Secure Communication — 設備用 IDevID/LDevID 私鑰做 TLS client auth，雙向認證。每次連線都帶著身份，後端認識你。
更新
Firmware Update — 安全更新韌體，anti-rollback 防 downgrade，Secure Boot 驗簽。更新要有簽名保護，不允許降級攻擊。
量測
Measured Boot — 每次開機量測所有 component，PCR 留下可驗證記錄。開機記錄員，Phase 2–3 的基礎。
驗證
Remote Attestation — NMS 定期要求設備提供 attestation quote，Pass/Fail 決定是否允許連線。定期向遠端報到，不乾淨就被切斷。
合規
CRA Evidence — 彙整 device identity、firmware integrity、key protection、attestation 記錄，作為合規評估的技術 evidence。把所有安全記錄整理好，幫 OEM 做 CRA 準備。

口頭問答練習 30 題
默背用 — 蓋住答案先回答再看
Q1. fTPM 和 vTPM 差在哪？
fTPM 跑在實體設備 TrustZone Secure World，保護真實硬體金鑰；vTPM 是 VM/QEMU 軟體模擬，信任基礎是 hypervisor。生產設備用 fTPM，開發測試才用 vTPM。
Q2. Soteria hRoT 為什麼不是 TPM？
Soteria 是 vendor-specific HW IP，透過 AHB MSG 命令操作，沒有 TSS2 API，不符合 TCG TPM 2.0 規範。功能類似（硬體信任根），但 API 和 evidence model 完全不同。
Q3. OP-TEE 跑在哪？跑在 Soteria 上嗎？
OP-TEE 跑在主 ARM SoC 的 TrustZone Secure World，不是跑在 Soteria。Soteria 是獨立 AHB HW IP，被 OP-TEE Secure World driver 透過 AHB 存取。
Q4. IDevID 和 LDevID 差在哪？
IDevID：出廠燒錄，與設備終身綁定，不可更換（OTP）。LDevID：現場發放，可更換 / 可撤銷（類似工作證）。兩者都要求 non-exportable private key（IEEE 802.1AR）。
Q5. mTLS 怎麼用 Device Identity？
設備用 IDevID/LDevID 私鑰做 TLS client auth，後端驗設備 cert；設備也驗後端 server cert。私鑰保護在 TPM/hRoT 邊界內（non-exportable），簽名在硬體內完成，私鑰不外洩。
Q6. Secure Boot 和 Measured Boot 差在哪？
Secure Boot = 守門員，驗簽，失敗就不開機。Measured Boot = 記錄員，量測 hash 存 PCR，允許開機但留記錄。一個擋，一個記，要一起用才完整。
Q7. Measured Boot 和 Remote Attestation 差在哪？
Measured Boot：本地記錄，存在 PCR。Remote Attestation：用 TPM AIK 簽名 PCR 快照，傳給遠端 Verifier，讓外部驗證「設備開機狀態是乾淨的」。
Q8. CRA-ready 和 full CRA compliance 差在哪？
CRA-ready：技術控制到位、可準備 evidence、能支援合規評估。Full compliance：通過 conformity assessment、取得 CE marking，法律責任在 OEM。FiduciaEdge 提供技術服務，不承擔 OEM 合規責任。
Q9. 什麼時候需要 OP-TEE fTPM？
需要 TPM 2.0 API 相容（TSS2）、PCR/Measured Boot、TPM2_Quote attestation、ECDSA，或客戶要求標準 TPM evidence 時。前提：SoC 支援 ARM TrustZone。
Q10. 為什麼 TX8 先研究 Soteria-native path？
TX8 已有 Soteria 且 AHB driver 就緒；TX8 TrustZone 支援尚未確認；記憶體佔用低；若只需 DevID/mTLS 不需要完整 fTPM。Soteria-native 是更快的 PoC 路線（前提：確認 Soteria API 能力）。
Q11. Device Trust Abstraction Layer 是什麼？
Backend-agnostic 介面層（dt_generate_key / dt_sign / dt_generate_csr / dt_store_cert / dt_get_attestation_evidence），讓 TTPS DI 不直接依賴底層 RoT API。不同平台接不同後端，未來換後端不需重寫上層邏輯。
Q12. Black Key 是什麼？
Soteria 的 HW key wrapping 機制：TRNG 生隨機 key → ROK 加密 → 輸出 ENZMK + ENBK + MAC（Black Key）。OP-TEE 只持有加密後版本，raw HUK 永不離開 Soteria。
Q13. Non-exportable private key 是什麼，為什麼重要？
IEEE 802.1AR 要求 DevID 私鑰只能在硬體邊界內使用，不能被導出。沒有這個保護，攻擊者可複製私鑰，設備身份安全失效。TPM 用 FIXED_PARENT 實現，Soteria 靠 Black Key（待確認）。
Q14. CSR 如何在 Soteria-native path 生成？
ASN.1 encoding 在 SW 層完成（組裝設備資訊和公鑰），簽名由 Soteria RSA（MSG0=0x3）執行。Soteria 不提供完整 CSR API，需上層 SW 配合。
Q15. PLANET 的切入重點？
高階 ARM：談 OP-TEE fTPM → mTLS → RA roadmap，三階段提案。Legacy MIPS：先做 feasibility，確認能否加 external SE/hRoT；不亂承諾 hardware RoT / non-exportable key / Remote Attestation。
Q16. TX8 的切入說法？
「TX8 的 primary RoT 是 Soteria hRoT。我們研究 Soteria-native DevID path（不用 OP-TEE fTPM）是否可行，因為 TX8 TrustZone 尚未確認。OP-TEE fTPM 是 candidate。設計保持 backend-agnostic，未來可接 attestation。」
Q17. MIPS 可以做 Remote Attestation 嗎？
❌ 不能承諾。無 hardware RoT 就沒有 PCR/Quote 基礎。只能做 feasibility study，評估能否外加 hRoT/SE。在未確認的情況下，不對 Legacy MIPS 承諾 Remote Attestation 能力。
Q18. Phase 1/2/3 是什麼？
Phase 1：Device Identity + mTLS。Phase 2：Secure Provisioning + Onboarding。Phase 3：Measured Boot + Remote Attestation（需 PCR/Quote，Soteria TBC）。
Q19. 為什麼要 backend-agnostic 設計？
不同客戶有不同 RoT（x86 hTPM / ARM fTPM / TX8 Soteria）；架構要保留未來切換後端的能力；避免 TTPS DI 上層邏輯重寫。一套服務能服務所有平台，靠 Device Trust Abstraction Layer 隔離差異。
Q20. Secure Element 適合什麼？
外接安全晶片（I2C/SPI/USB），適合 Legacy 平台補強（加裝不改主板）。PKCS#11 API，Phase 1/2 可行。通常不支援 PCR / attestation quote，Phase 3 需另確認。
Q21. PUF 是什麼？
Physical Unclonable Function，利用晶片製造差異產生設備唯一 fingerprint，作為 key derivation 基礎（如 NXP ELE 內建 PUF）。PUF 本身不直接提供 TPM 功能，需搭配 key management。
Q22. IEEE 802.1AR 定義了什麼？
DevID 的 IEEE 標準：non-exportable private key 要求、IDevID（出廠不可換）/ LDevID（現場可換）規範、X.509 cert 格式、lifecycle 管理。是 DevID 設計的法規依據。
Q23. BRSKI 是什麼？
Bootstrap RFC 8995，零觸碰自動上線協議。設備開機後用 IDevID 向 Registrar 認證，取得組織的 Domain Certificate（即 LDevID）。是自動化 onboarding 的標準化方法。
Q24. CRA 全面強制執行是哪天？違規多少？
2027-12-11。違規最高 €15M 或全球年營收 2.5%（取較高）。2026-09-11 漏洞通報義務先生效。這是對客戶說明緊迫性的關鍵數字。
Q25. 如何向沒聽過的人解釋 Soteria hRoT？
「TX8 有一個內建硬體安全模組叫 Soteria，類似 TPM 的角色，負責保護 key、做加密運算和驗證開機。它透過 AHB 匯流排存取，有自己的 RISC-V 處理器和安全 OTP。我們在研究讓它直接支援設備身份認證。」
Q26. HUK 是什麼？
Hardware Unique Key，設備唯一根密鑰。Soteria 用 TRNG 生成並存在 OTP，是 Black Key 機制的根和 OP-TEE Secure Storage 的加密基礎。HUK 永不離開 Soteria。
Q27. 為什麼 John 擔心 OP-TEE 記憶體？
OP-TEE Secure World 需要 4–16 MB（TF-A + OP-TEE OS + fTPM TA），在資源緊張的嵌入式設備上是顯著負擔。如果只需要 DevID/mTLS，Soteria-native 的記憶體佔用明顯更低。
Q28. Soteria INSTALL_ROK 做什麼？
安裝 Root of Key（ROK）到 Soteria OTP，通常在製造端執行，需要 ROK password 認證。ROK 是 Black Key 機制的根，安裝後不可更改（MSG0=0x11）。
Q29. swtpm 是什麼，FiduciaEdge 怎麼用？
開源 vTPM 模擬器（KVM/QEMU），FiduciaEdge 用於 CI/CD pipeline 測試，讓開發者不需要真實 TPM 就能跑測試。絕對不能用於生產 IoT 設備。
Q30. FiduciaEdge TTPS 的三條鐵律？
① 不說「guarantee full CRA compliance」，說「CRA-ready foundation」。② fTPM ≠ vTPM，永遠不混用。③ OP-TEE 不跑在 Soteria 上，OP-TEE 跑在主 SoC TrustZone，Soteria 是被 OP-TEE 存取的 AHB HW 模組。
