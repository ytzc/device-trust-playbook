B

目前的理解

請 John 確認這些理解是否正確。

  • x86 平台：預設使用 hTPM（hardware TPM），可能是 integrated TPM 或 discrete TPM。這是 default path，走 TSS2 / OpenSSL TPM2 Provider 整合。
  • ARM + TrustZone / OP-TEE 平台：使用 optee_ftpm TA，執行於 OP-TEE Secure World。這是 ARM 平台的 firmware TPM 路線，走相同的 TPM 2.0 API（TSS2 / TPM2 Provider），只是底層是 firmware 而非實體晶片。
  • Techmation TX8：使用 Soteria hRoT。預計不走 TPM API，而是透過 Soteria / vendor API 整合。Phase 1/2 可行，Phase 3（Remote Attestation）需另確認 Soteria 是否支援 attestation quote。
  • fTPM（firmware TPM）：用於實體 IoT / embedded / ARM device，執行於 TEE / TrustZone Secure World。可能基於 Microsoft TPM 2.0 Reference Implementation。例如 OP-TEE fTPM TA。
  • vTPM（virtual TPM）：主要用於 VM / KVM / QEMU 等虛擬化環境。常見實作是 swtpm。不應用於生產實體設備。
  • swtpm：軟體 TPM 模擬器，主要用於 KVM / QEMU 開發與測試環境中的 vTPM。
  • CRA support ≠ 只做 TPM：RoT / TPM / fTPM / hRoT 是 CRA-ready security foundation 的技術基礎，但不等於完整 CRA compliance。CRA 還需要 vulnerability handling、security updates、documentation、risk assessment、evidence、product lifecycle process 等。
  • PLANET Legacy MIPS：無 hardware RoT，只能提供 gap analysis + compensating controls，不可承諾 hardware-bound identity 或 Remote Attestation。

D

fTPM vs vTPM — 這兩者不一樣

John 特別提醒這個區分很重要，不要混用。

⚠ 重要區分： fTPM（firmware TPM）≠ vTPM（virtual TPM）。這是兩種完全不同的使用場景。請在技術說明和文件中嚴格區分。
比較項目fTPM（Firmware TPM）vTPM（Virtual TPM）
使用場景實體 IoT / embedded / ARM deviceVM / KVM / QEMU 虛擬化環境
信任基礎TEE / TrustZone / Secure World firmware isolationHypervisor / QEMU emulator（軟體）
硬體隔離TrustZone hardware memory isolation（TZASC）無實體隔離，軟體模擬
常見實作OP-TEE fTPM TA、Microsoft TPM 2.0 Reference Implementation（msft-fTPM）swtpm（software TPM 2.0 emulator）
TPM 2.0 API 相容是（TSS2 / TPM2 Provider 可直接使用）是（相同 API，但信任基礎是軟體）
適合 PLANET embedded gateway是（ARM gateway 有 TrustZone）不適合（需要 hypervisor）
適合 VM 環境不適合（embedded 用）是（KVM/QEMU 標準方案）
CRA production 場景是，用於實體設備不可，虛擬化 TPM 不符合 production RoT
private key 保護強度強（TrustZone hardware isolation）依 hypervisor 安全性，相對較弱
Measured Boot / PCR支援（OP-TEE fTPM 有 PCR）支援（但可信度取決於 hypervisor）
Microsoft 基礎Microsoft TPM 2.0 Reference Implementation 是許多 ARM fTPM 的基礎實作swtpm 是獨立開源專案

OP-TEE fTPM TA 的定位

  • OP-TEE（Open Portable Trusted Execution Environment）是 ARM TrustZone 的開源 TEE 實作
  • fTPM TA（Trusted Application）是跑在 OP-TEE Secure World 的 TPM 實作
  • 通常基於 Microsoft TPM 2.0 Reference Implementation 移植
  • 對外暴露標準 TPM 2.0 API → TSS2 / TPM2 Provider 可直接使用
  • Private key 在 TrustZone Secure World，Normal World 無法直接讀取
  • 是 PLANET ARM gateway 的主要 RoT 路線

swtpm 的定位

  • swtpm 是 Stefan Berger（IBM）開發的開源軟體 TPM 2.0 模擬器
  • 主要用途：KVM / QEMU VM 的 vTPM 後端
  • 提供與實體 TPM 相同的 API 介面，方便開發測試
  • KVM 透過 QEMU 的 -tpmdev 參數啟用 swtpm vTPM
  • 信任基礎是 hypervisor，不應用於生產 embedded 設備
  • FiduciaEdge 使用它做 CI/CD 測試環境，不是交付產品
E

TPM API vs Soteria hRoT API

Techmation TX8 為什麼不一定要走 TPM API。

TPM API（標準化）

  • 標準： TCG（Trusted Computing Group）TPM 2.0 specification
  • 軟體介面： TSS2（TPM Software Stack 2）library
  • OpenSSL 整合： OpenSSL TPM2 Provider（tpm2-openssl）
  • PKCS#11： tpm2-pkcs11 bridge
  • 功能： Key generation, signing, PCR extend, attestation quote, NV storage
  • 優點： 標準化、可攜性高、工具生態完整
  • 適用： x86 hTPM、ARM fTPM（OP-TEE）

Soteria hRoT API（vendor-specific）

  • 來源： Techmation 的 Soteria hardware RoT 模組
  • 介面： Vendor SDK / proprietary API（非 TCG 標準）
  • 整合方式： 需開發 custom adapter layer 對接 TTPS DI flow
  • 功能（待確認）： Secure key storage、device identity、可能有 firmware integrity
  • Attestation： Phase 3 需確認 Soteria 是否有 quote mechanism
  • 優點： 硬體 RoT，不需要 ARM TrustZone
  • 缺點： 工程量較大，可攜性低
結論： TX8 不需要硬套 TPM terminology。只要 Soteria hRoT 能提供 secure key storage + device identity + firmware integrity + attestation evidence foundation，就可以作為 CRA-ready 的 RoT foundation。關鍵是要確認 Soteria API 具體支援哪些功能。
能力需求TPM API（標準）Soteria hRoT API（TX8）CRA support 角色
Secure key storage是待確認Device identity foundation
Device identity（不可提取 key）是待確認CRA Annex I (2)(d)
Firmware integrity / Secure Boot需另確認待確認CRA Annex I (2)(f)
PCR-like measurement slots是（PCR 0–23）待確認Measured Boot / Phase 3
Attestation quote / evidence是（TPM Quote）Phase 3 阻擋條件Remote Attestation
Standard API / 工具生態完整（TSS2 / OpenSSL）需 custom adapter工程複雜度
F

CRA Support 定位說法

向 John 確認這個定位方向，並用於後續客戶溝通。

Device Trust & Platform Security Foundation for CRA Compliance Support

我們提供的是 CRA compliance support 所需的技術基礎。這不等於完整 CRA compliance——CRA 的完整合規還需要 OEM 執行 conformity assessment、建立 vulnerability handling 程序、提交文件等。

替代說法：CRA-Ready Device Trust & Platform Security Solution

RoT 在 CRA support 中的角色

  • Device identity：hardware-bound、不可偽造的設備 ID（Annex I (2)(d)）
  • Key protection：VPN/mTLS 私鑰不離開硬體邊界（Annex I (2)(e)）
  • Firmware integrity：Secure Boot + Measured Boot（Annex I (2)(f)）
  • Attestation foundation：RA quote 的信任根（Annex I (2)(f)(k)(l)）

CRA 還需要什麼（不是 RoT 範圍）

  • Vulnerability handling / PSIRT 程序
  • Security updates pipeline + OTA 管理
  • Product risk assessment（OEM 責任）
  • CRA Annex I 技術文件與 conformity assessment
  • Product security contact / CVD policy
  • SBOM 生成與維護 pipeline（OEM 端）
