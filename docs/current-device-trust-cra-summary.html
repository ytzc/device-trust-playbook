Executive Summary 執行摘要

我們建立的是 Device Trust & Platform Security 能力，CRA 是其中一個重要的合規驅動場景，但整體能力遠超出 CRA 本身。

核心定位： FiduciaEdge 提供 CRA 所需安全控制的技術實作基礎，協助 OEM 建立 CRA-ready 產品安全架構。Conformity assessment 與 CE marking 法律責任仍在 OEM 製造商。
🔑

Device Identity

IDevID / LDevID · Hardware-bound

每台設備唯一、不可匯出的 device key + cert，儲存於硬體保護邊界（fTPM / SE / hRoT）。

📌 CRA Annex I (2)(d) AuthN & Identity
🛡

Root of Trust

TPM 2.0 / fTPM / hRoT / SE

Private key 永不離開硬體保護邊界。ARM TrustZone fTPM / hTPM / Soteria hRoT / External SE。

📌 CRA Annex I (2)(e)(k) Confidentiality & Mitigation
🔧

Secure Provisioning

TTPS DI · FDO · Zero-touch

TTPS DI service 已在 Ubuntu+TPM 驗證。Phase 1 = 移植至 MTK OpenWRT + fTPM。FDO 協定支援 zero-touch onboarding。

📌 CRA Annex I (2)(b) Secure-by-default
📦

Firmware Integrity

Secure Boot · Measured Boot · SBOM

Secure Boot 確保 boot chain 可信。Measured Boot 將每個 boot 階段 hash extend 至 PCR-like registers。SBOM 由 OEM release key 簽署。

📌 CRA Annex I (2)(b)(f) Integrity
📡

Remote Attestation

Measured Boot · Quote · NMS Policy

RA client 產生帶簽章的 attestation report；NMS verifier 比對 Known-Good baseline；Pass / Fail / Unknown verdict 控制管理存取。

📌 CRA Annex I (2)(f)(k)(l) Integrity, Monitoring
CRA 時程： 2026/06/11 — Conformity assessment bodies 通知規定開始適用（今日）｜ 2026/09/11 — 漏洞主動利用通報義務｜ 2027/12/11 — CRA 全面強制執行（距今約 18 個月）｜罰則：最高 €15M 或年營收 2.5%

Current Customer / Project Context 客戶與場景

目前涉及的主要客戶與技術場景。

PLANET Technology — Gateway 產品線

CRA Important Class I 風險 三階段 RA 提案

PLANET 為台灣網路設備製造商，高階 Gateway 可能落入 CRA Important Class I（CRA Annex III），需通過 harmonized standard 合規或第三方審查。FiduciaEdge 提出三階段 RA 提案（以 MTK ARM TrustZone + fTPM 平台為主）。

  • Phase 1：TTPS DI 移植（Ubuntu+TPM → MTK OpenWRT + fTPM）— hardware-bound device identity
  • Phase 2：VPN/mTLS private key 移入 TrustZone；PKCS#11 / TPM2 Provider 整合
  • Phase 3：Measured Boot → PCR；RA client；NMS Verifier + Policy Engine

⚠ 關鍵前提： MIPS 架構本身不是阻礙——問題在於特定 MIPS SoC 缺乏 hardware RoT。無 hardware RoT 的平台只能提供 gap analysis + compensating controls。

Techmation TX8

有 Soteria hRoT Vendor-specific API

TX8 搭載 Soteria hRoT（vendor-specific API，非 TPM2 標準 API）。Phase 1/2 可行。Phase 3 Remote Attestation 需確認 Soteria 是否支援 attestation quote mechanism。

  • 需開發 custom adapter layer（工程量高於 TPM2 Provider path）
  • Soteria attestation quote capability 為 Phase 3 阻擋條件

i.MX93 / NXP EdgeLock 2GO / TTPS / FDO

ELE + AHAB + TrustZone Root CA sovereignty 待決

i.MX93 含 ELE（EdgeLock Secure Enclave）、AHAB Secure Boot、TrustZone。SESIP Level 3 / PSA Level 3 認證為技術佐證（不等同 CRA compliance）。

  • 衝突風險： NXP EL2GO 若控制 Root CA，FiduciaEdge 的 Chain of Trust 設計建立在 NXP 信任錨點上 → FiduciaEdge 失去架構主導權
  • FiduciaEdge 立場： Chain of Trust 定義、Attestation 設計、Threat Modeling 應由 FiduciaEdge 主導
  • AN14601 Rev 1.1（NXP）明確聲明：不保證 CRA 法律確定性，僅為技術路徑指引

Mitwell e-Box

CRA Compliance Workshop 待確認

FiduciaEdge 正為 Mitwell 進行 CRA compliance workshop。涉及 NXP EL2GO 整合。Root CA sovereignty 是關鍵考量。具體產品 SoC 型號、EL2GO 整合邊界、Root CA 歸屬：需人工確認（Mitwell Proposal DOCX 未完整讀取）。

Legacy MIPS Switch / Bridge

無 hardware RoT Compensating Controls only

部分舊有產品使用 MIPS SoC（優化封包處理，無 TrustZone / hardware TPM 接頭）。

  • 可提供：Gap analysis + SBOM + signed firmware update + mTLS（軟體金鑰）+ CVD policy
  • 不可承諾：Hardware-bound identity、non-exportable key、Remote Attestation evidence 可信度
  • 若有 External SE + PKCS#11：Phase 1/2 仍可能可行（需確認 SE 型號）

Capability Model 能力模型

Device Trust 技術棧的各層能力，從 Device Identity 到 CRA Evidence。

🔑 Device Identity

Phase 1
目的

IDevID / LDevID，hardware-bound，non-exportable private key。每台設備唯一不可偽造的身份。

對 CRA readiness

直接對應 Annex I (2)(d) Authentication & Identity Management。所有後續功能的信任基礎。

平台相依性

高。需要 hardware RoT。無 hardware RoT 只有軟體金鑰（可信度弱）。

🔒 Secure Provisioning

Phase 1
目的

製造時或部署時安全注入 device key + cert。Zero-touch / minimal-touch。TTPS DI（已驗證）+ FDO 協定。

對 CRA readiness

對應 (2)(b) Secure-by-default；出廠即具備 hardware-bound identity，無不安全預設狀態。

平台相依性

高。Key 必須在 hardware RoT 中產生。

🛡 Root of Trust Integration

Phase 1–2
目的

將平台 hardware RoT 正確整合到 OS/Application 層，提供 hardware-isolated key operations。

對 CRA readiness

(2)(d)(e)(k)；private key 不離開 hardware boundary。

各平台 API

x86 hTPM → TSS2 / TPM2 Provider｜ARM fTPM → 同 hTPM API｜TX8 → Soteria vendor API｜External SE → PKCS#11

📦 Firmware Integrity

Phase 2–3 前提
目的

確保設備運行的 firmware 是原廠授權版本，未被篡改。Build-time signing + deploy-time verification。

對 CRA readiness

(2)(f) Integrity；(2)(b) Secure-by-default。

平台相依性

高。需要 Secure Boot（boot chain signature verification）。PLANET 目標平台 Secure Boot 狀態待確認。

📏 Measured Boot

Phase 3 前提
目的

在 Secure Boot 基礎上，將每個 boot 階段的 cryptographic hash extend 到 hardware-write-once PCR-like registers。

對 CRA readiness

Phase 3 Remote Attestation 的核心前提。沒有 Measured Boot 就沒有 verifiable boot integrity evidence。

重要注意

PKCS#11-only 平台無此能力。需 hardware write-once registers。

📡 Remote Attestation

Phase 3 目標
目的

NMS 遠端驗證設備 boot + runtime integrity，依驗證結果做 policy decision（Pass/Fail/Unknown）。

對 CRA readiness

(2)(f)(k)(l)；tamper-evident runtime evidence，支援 attestation-gated access control。

重要提醒

Remote Attestation 是 roadmap，不應對所有平台立即承諾。需逐平台確認完整能力棧。

📋 CRA Evidence Readiness

全程
目的

為 OEM conformity assessment 準備技術佐證：CRA Annex I mapping 文件、RA audit trail、SBOM、security architecture 說明。

對 CRA readiness

支援 OEM 執行 conformity assessment 的技術面準備；不等同合規本身。

平台相依性

低（文件層）。但技術佐證強度取決於平台能力。

Remote Attestation Roadmap RA 導入路線

Remote Attestation 是 roadmap，不是立即可用的功能。需逐平台確認能力棧後再決定可交付的 Phase。

Phase 3 必備條件（缺一不可）： ① Secure Boot（boot chain 信任起點） ② Measured Boot（boot stage hash extend 至 hardware-write-once registers） ③ PCR-like measurement slots（hardware write-once） ④ Signed attestation quote mechanism ⑤ NMS verifier integration
— PKCS#11 只解決條件 ④ 的一部分（key operation），不提供條件 ①②③。

Assessment + Identity Foundation

Phase 1 前：評估 + 基礎建立
  • 目標平台 hardware capability audit（SoC 型號確認）
  • RoT API 確認（TPM2 / fTPM / SE / hRoT）
  • 建立 hardware-bound device identity
  • TTPS DI 移植或新整合
成果：每台設備有 hardware-bound cert；private key non-exportable

RoT Integration + Firmware Integrity

Phase 2：Key protection + Boot readiness
  • VPN/mTLS hardening（PKCS#11 / TPM2 Provider）
  • Secure Boot 確認或建立
  • SBOM generation + signing pipeline
成果：management channel hardened；firmware integrity foundation

Measured Boot / RA / CRA Evidence

Phase 3：Full attestation + compliance evidence
  • Measured Boot integration
  • RA Client daemon
  • NMS Verifier + Known-Good Baseline DB
  • Policy Engine（Pass/Fail/Unknown）
  • CRA evidence documentation
成果：NMS 依 trust verdict 控制 management access；CRA Annex I 技術佐證

Gary's PLANET NMS CRA Enforcement Matrix

來源：PLANET_NMS_CRA_Enforcement_Matrix (GG1).xlsx（Gary 分析）— 對照 PLANET NMS 現有功能、CRA 強制條文、提案強化方向與商業效益。

本矩陣從 PLANET NMS 產品視角出發，與 FiduciaEdge 三階段 RA 提案在技術方向上高度一致：(2)(d) → Phase 1，(2)(e) → Phase 2，Part II (1) 與 (2)(f) → Phase 3。

Annex I Sec 1(3)(d) — Unauthorized Access Protection

Phase 1 Device Identity

要求所有連接設備具備強身份驗證與唯一身份追蹤。

現有 PLANET NMS

Software-Defined Device Identity
標準軟體層簽發的 cryptographic certificate、API keys、OS 層管理的 credentials。

提案強化

Hardware-Rooted Identity（CRA Trust Anchor）
佈建 TWCA-bound identity certificate，cryptographic 綁定鎖入 ARM TrustZone，建立不可竄改的唯一設備識別碼。

商業 & 安全效益

Zero-Identity Theft Risk
Hardware-bound identity 無法被複製或偽造，保證完整 supply chain 追蹤與不可否認性。軟體金鑰可被 OS-level 漏洞複製，hardware key 不可。

Annex I Sec 1(3)(e) — Data Confidentiality

Phase 2 VPN / mTLS Key Protection

要求使用當代技術水準的加密機制，保護傳輸中資料與遠端連線。

現有 PLANET NMS

Standard Network Layer VPNs
內建軟體 VPN（IPSec、OpenVPN、SSL VPN），在主作業系統環境中執行，private key 儲存於 OS 檔案系統。

提案強化

Hardware-Bound VPN（Cryptographic Hardening）
將 private session key 直接錨定在 secure element 或 ARM TrustZone 內。key operations 在 Secure World 執行，Normal World 只取得 signature result。

商業 & 安全效益

Breach Isolation
即使攻擊者取得主 OS 的完整 root 存取，private cryptographic key 仍完全無法取得，遠端管理通道持續受到保護。

Annex I Sec 2(1) — Vulnerability Management & SBOM

Phase 3 SBOM + Measured Boot

要求有文件記錄的 SBOM，搭配驗證完整性並防止竄改的機制。

現有 PLANET NMS

Software Integrity Verification
Firmware 部署 pipeline 中的 cryptographic hash 驗證機制，確保系統更新成功完成。

提案強化

Consolidated SBOM & Measured Boot Integrity
Build time 產生 cryptographically signed SBOM，搭配 ARM TrustZone 強制執行的 Measured Boot 序列（OP-TEE / TF-A 架構）。

商業 & 安全效益

Active Supply Chain Enforcement
標準方案將 SBOM 視為被動合規文件；此架構在開機時主動執行 SBOM。TrustZone 層量測系統 binary，若未授權軟體偏離已簽署 baseline 則阻擋執行。

Annex I Sec 1(3)(f) — Tamper Proofing & Availability

Phase 3 TrustZone Memory Isolation

要求對竄改、修改與資料毀損具備實體與系統性的韌性。

現有 PLANET NMS

Framework-Level Cyber Resilience
標準 process-level 網路安全框架與安全日誌，針對標準網路基礎設施部署優化。被動偵測為主。

提案強化

Hardware-Enforced System Resilience
在 silicon 層設定實體 TrustZone 記憶體控制器（TZASC / TZMA），在硬體層隔離安全進程與金鑰，與主 OS 完全分離。

商業 & 安全效益

Immutable CRA Compliance
從被動 software-dependent 框架轉移為主動 hardware-level 記憶體防護，防止未授權 runtime data 存取，降低 2026-09 強制執行帶來的企業法律責任。

Phase 1 — 安全身份佈建 [10w]

Provision Secure Identity via Hardware Root of Trust

OBJECTIVE

將硬體綁定的設備身份與憑證佈建到矽晶層，讓應用程式可密碼學驗明設備身份與韌體完整性。

OUTCOME

不可偽造、hardware-bound、密碼學不可否認的設備身份。私鑰在 ARM TrustZone 內產生且永不外露，對應 CRA Annex I §1(3)(d)。

ENGINEERING TASKS
  • Initialize HRoT on ARM TrustZone [6w]
    部署 fTPM TA，暴露 TPM 2.0 API 至 OpenWRT
  • TWCA Device Identity Provisioning Pipeline [4w]
    製造端 toolchain，enclave 內產生 keypair + TWCA 憑證鎖入 secure storage
Pre-req： MTK BSP 須已含 TF-A（未設定 +3w Lead Time）
Out of Scope： 整合 PLANET 客製 BSP 產品分支（~3w）、GUI 管理介面

Phase 2 — 硬體綁定 VPN 強化 [9w]

Hardware-Bound VPN for Isolated Management Channels

OBJECTIVE

在專用網路切片上建立獨立加密通道，完全隔離管理平面與資料流量。

OUTCOME

即便主機 OS 被入侵，管理通道仍安全。VPN 私鑰鎖在 TrustZone 內，無法被 root 用戶讀取或提取。對應 CRA 資料機密性要求。

ENGINEERING TASKS
  • TrustZone Crypto Key & Engine Offloading [4w]
    OpenSSL TPM2 Provider / PKCS#11 橋接 VPN 引擎至 fTPM Enclave
  • mTLS Isolation Verification & Testing [2w]
    驗證 mTLS 私鑰無法被 OpenWRT root 讀出或 dump
  • Network Bandwidth & Crypto Benchmarking [3w]
    驗證 enclave crypto offload 不影響路由吞吐量
Out of Scope： OpenWRT nftables / VLAN 網路切片配置（~2w，PLANET 端負責）

Phase 3 — Remote Attestation [25w]

Boot & Runtime Integrity Remote Attestation

OBJECTIVE

設備在開機序列動態量測自身執行狀態，產生 Remote Attestation Report，向 NMS 驗證服務證明完整性。

OUTCOME

主動供應鏈驗證。每個 boot 階段 hash extend 至 TrustZone 防竄改 slot，RA Report 與 PLANET 簽署 SBOM baseline 比對。偏差 → NMS 拒絕管理平面存取 + 合規告警。支援 2026-09-11 起的漏洞通報義務。

PRE-REQUISITES（PLANET 端）
  • Phase 1 硬體綁定設備憑證已佈建
  • PLANET OpenWRT 24 build 環境可自動產生 SPDX/CycloneDX SBOM
  • SBOM 以 PLANET Corporate Release Key 加密簽署
  • MTK ARM bootloader pipeline (BL2→BL32) 已設定 Secure Boot
ENGINEERING TASKS
  • Measured Boot Instrumentation (BL2→BL32) [8w]
    BL2-BL32 bootloader Measured Boot extension，hash extend 至 fTPM slot
  • OpenWRT Kernel Runtime Integrity Verification [3w]
    Kernel runtime integrity hooks 接入 fTPM Enclave
  • Attestation Client & Challenge Protocol [8w]
    User-space RA client daemon，從 fTPM fetch signed quote，打包 RA Report
  • Standalone Device Onboarding & Attestor Service [6w]
    網路端驗證服務，接收 RA Report、驗簽、比對 SBOM baseline、Pass/Fail 判定
Quantifiable Output： Measured Boot patches + RA client daemon + containerized Attestor service + web UI console
Out of Scope： PLANET 內部 CI/CD SBOM 簽署管線（FE 提供規格指導）、NMS 核心平台程式碼修改
