03

各路線詳細說明

每個決策路線的技術架構、整合方式與主要考量。

Path X86：x86 + hTPM（hardware TPM）

Default Path已驗證

x86 平台通常內建 discrete 或 integrated TPM 2.0 晶片，符合 TCG specification。TTPS DI 已在 Ubuntu + TPM 環境驗證。

  • RoT：硬體 TPM 晶片（discrete：例如 Infineon SLB9670；integrated：Intel PTT / AMD fTPM on PSP）
  • API：TSS2（TPM Software Stack 2）→ OpenSSL TPM2 Provider → PKCS#11 bridge
  • 三階段：Phase 1（device identity）→ Phase 2（VPN/mTLS key hardening）→ Phase 3（Measured Boot + RA）完整適用
  • 現狀：Phase 1 TTPS DI 已驗證；Phase 2/3 路線清楚

Path ARM-A：ARM + TrustZone + OP-TEE fTPM TA

主要交付目標規劃中

ARM 平台使用 OP-TEE（Open Portable TEE）作為 TrustZone Secure World 環境，在其中運行 fTPM TA（Trusted Application），提供與 hTPM 相同的 TPM 2.0 API 介面。

  • RoT：OP-TEE Secure World + fTPM TA（通常基於 Microsoft TPM 2.0 Reference Implementation）
  • API：相同的 TSS2 / TPM2 Provider，對上層應用透明
  • 前置條件：BSP 需含 TF-A（Trusted Firmware-A）+ OP-TEE OS + fTPM TA；Secure Boot 啟用
  • PLANET 適用性：MediaTek ARM gateway 若 BSP 已含 OP-TEE + fTPM，則此為主要路線
  • Phase 1 工程任務：TTPS DI 移植（Ubuntu+TPM → MTK OpenWRT + OP-TEE fTPM）

Path TX8：Techmation TX8 + Soteria hRoT

評估中Phase 3 待確認

TX8 搭載 Soteria hardware RoT 模組，透過 vendor-specific API 存取。不走標準 TPM API，需要開發 custom adapter layer。

  • RoT：Soteria hRoT（hardware RoT，非 TPM）
  • API：Soteria vendor SDK → 需開發 custom adapter 接 TTPS DI flow
  • Phase 1/2：可行（secure key storage + device identity + key protection）
  • Phase 3 阻擋條件：Soteria 是否支援 attestation quote / measurement mechanism（待確認）
  • 工程量：高於標準 TPM2 Provider path（需 custom adapter）

Path MIPS：Legacy MIPS — Feasibility Study First

無 hardware RoT補償控制

部分舊有產品使用 MIPS SoC（優化封包處理，通常無 TrustZone / hardware TPM 接頭）。MIPS 架構本身不是阻礙——問題在於缺乏 hardware RoT。

  • 第一步：Feasibility study — 評估該 MIPS SoC 是否能加入 external hRoT 或 secure element
  • 可加入 external SE：Phase 1/2 透過 PKCS#11 仍可能可行（需確認 SE 型號與介面）
  • 無法加入：只能提供 gap analysis + compensating controls（簽名 firmware update / mTLS 軟體金鑰 / CVD policy）
  • 不可承諾：hardware-bound identity、non-exportable key、Remote Attestation evidence 可信度

Path VM：VM / KVM / QEMU — vTPM / swtpm

開發測試用不可用於生產

虛擬化環境使用 vTPM（virtual TPM），常見實作為 swtpm。信任基礎是 hypervisor，不適合生產嵌入式設備。

  • RoT：swtpm（software TPM emulator，Stefan Berger / IBM）
  • 用途：CI/CD pipeline 測試、開發環境驗證、功能性測試
  • API：與實體 TPM 相同（TSS2 / TPM2 Provider），便於移植測試
  • 限制：無實體隔離，安全性取決於 hypervisor；不可用於生產 embedded 設備
04

決策理由

為何這樣選擇 RoT 方法。

為什麼 x86 用 hTPM 而非軟體方案

  • x86 平台幾乎都有內建 TPM 2.0 晶片，啟用成本低
  • Hardware TPM 提供實體隔離，private key 在晶片內部，OS 無法直接讀取
  • 標準化 TSS2 API 生態完整，工程整合相對成熟
  • Phase 3 所需的 PCR registers 是 TPM 標準功能

為什麼 ARM 優先 OP-TEE fTPM 而非 external SE

  • ARM TrustZone 是 SoC 內建硬體機制，不需額外硬體成本
  • OP-TEE + fTPM 提供相同的 TPM 2.0 API，移植 x86 方案成本低
  • TrustZone 隔離強度已被廣泛驗證（PSA Certified、SESIP）
  • external SE 雖然更安全，但 BOM 增加且整合複雜度更高

為什麼 TX8 不強制走 TPM API

  • TX8 已有 Soteria hardware RoT，強制加 TPM 晶片代表重複硬體
  • Soteria API 可以提供 secure key storage / device identity 等等效功能
  • 不需要硬套 TPM terminology；只要能提供 RoT 功能即可作為 CRA foundation
  • custom adapter 工程量雖高，但避免硬體重設計

為什麼 Legacy MIPS 先做 feasibility study

  • MIPS 本身不是問題——問題是特定 SoC 是否有 hardware RoT 接頭
  • 先評估再決定，避免預先宣告「無法做」或「可以做」
  • external SE 是一個可能路徑，需確認 MIPS SoC 介面相容性
  • 若確認無法加入 hardware RoT，才正式進入 gap analysis 模式
